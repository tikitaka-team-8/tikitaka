## 무엇을 개선했는지

1. **페이지네이션 도입 (2026-09-16)** — `GET .../seats`가 매 요청마다 세션의 전체 좌석(3,008석)을
   정렬·직렬화해서 내려주던 것을, `page`/`size`(기본 0/50, 최대 200) 파라미터로 필요한 만큼만
   내려주도록 변경. `ScheduleSeatJpaRepository.findSeats`를 `Page<ScheduleSeat>` 반환으로 변경.
2. **필드 프로젝션 (2026-09-17)** — 응답에 실제 필요한 7개 컬럼만 JPQL 생성자 표현식(`SELECT new
   ...ScheduleSeatSummary(...)`)으로 조회하도록 추가(`SeatListReader.PROJECTION_ENABLED`). 기존에는
   감사 컬럼 포함 15개 컬럼짜리 `ScheduleSeat` 엔티티 전체를 하이드레이션했음.
3. **짧은 TTL 캐시 (2026-09-17)** — 동일한 `(eventSessionId, section, grade, page, size)` 조합
   조회 결과를 Caffeine(JVM 로컬 메모리)으로 2초간 캐싱(`SeatListCacheConfig.CACHE_ENABLED`,
   `CACHE_TTL_SECONDS`). 둘 다 코드 상수 토글이라 재빌드해야 반영됨(`application.yaml` 설정 아님).
4. (부수적으로) 큐 admission 토큰 TTL과 부하 유지시간이 충돌해 1,000 VU에서 대량 실패하던 **테스트
   스크립트 설계 결함**을 발견·수정 (서버 성능 문제 아님, `LOAD_RAMP`/`LOAD_DURATION` 단축).

## 병목 분석 (지금까지의 진단 흐름)

1. **09-15**: HikariCP 풀 미설정(추정)이 유력 후보로 지목됨 — 300~500 VU 구간 급격한 악화.
2. **09-16 재진단**: 실제 원인은 풀 크기가 아니라 **페이지네이션 미적용으로 인한 응답 크기(~450KB)**
   였음. 페이지네이션 적용 후 300/500/1,000 VU 모두 SLA 통과(PASS) — 단, 조건(ramp/duration)이
   Baseline과 달라 완전한 비교는 아니었음.
3. **09-16~17 재검증에서 재반전**: 조건을 최신 기본값으로 맞춰 다시 측정하니 300 VU부터 p95가 다시
   SLA를 위반(687ms). 응답 크기는 변함없이 작았으므로(~7.9KB), **응답 크기 문제와는 별개로 동시
   요청 수 자체가 늘면 지연이 늘어나는 한계**가 있는 것으로 재확인됨 — 09-16의 "PASS" 판정은 보류.
4. **09-17 (1,000 VU만)**: 프로젝션+짧은 TTL 캐시를 추가해 1,000 VU에서 avg/p50은 크게 개선(4~9배)
   됐지만, p95는 여전히 SLA 대비 2배 이상 — 처음엔 "평균 레이턴시"와 "꼬리 지연"이 서로 다른
   원인일 가능성으로 해석됐음.
5. **09-17 (300/500 VU 추가 측정)**: 같은 프로젝션+캐시 조합으로 300/500 VU를 재측정하니 둘 다

   아니라 **1,000 VU 부근에서만 나타나는 현상**이었던 것으로 범위가 좁혀짐 — 300~500 VU에서는
   프로젝션+캐시만으로 충분함.

**결론적으로, 지금까지 세 가지 조치(페이지네이션 → 프로젝션 → 캐시)로 300/500 VU 구간은 SLA를
만족시키는 데 성공했습니다. 남은 문제는 1,000 VU 부근에서만 나타나는 p95/p99 꼬리 지연이며, 서버 쪽
지표(HikariCP/JVM/GC) 없이는 이 남은 병목의 정확한 원인을 특정할 수 없는 상태입니다.**
