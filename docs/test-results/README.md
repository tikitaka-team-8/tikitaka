# 통합 테스트 결과

이 디렉터리는 서비스 안정화 기간에 수행한 **로컬 통합 테스트와 스테이징 검증 결과**를 시나리오별로 관리한다.

각 담당자는 맡은 시나리오를 작업 브랜치에서 실행하고, 발견한 문제를 수정한 뒤 동일한 조건으로 다시 검증한다. 재현에 필요한 Postman Collection, k6 스크립트, SQL과 자동화 스크립트는 저장소에서 함께 관리하고, 실제 실행 결과는 이 디렉터리에 기록한다.

## 진행 방식

```text
담당 시나리오 확인
→ 작업 브랜치 생성
→ 로컬 통합환경에서 최초 결과 확인
→ 문제 재현 및 원인 분석
→ 필요한 코드 보완
→ 동일 조건으로 재검증
→ 실행 자료와 local-result.md 작성
→ develop 대상 PR 생성
```

모든 로컬 시나리오가 안정화된 후에는 최신 `develop`의 Commit SHA를 고정하여 스테이징을 배포한다. 스테이징에서는 로컬 전체 테스트를 반복하지 않고, 팀에서 선정한 대표 시나리오를 실행하여 배포·네트워크·서버 자원에 따른 환경 차이를 확인한다.

## 결과 상태

| 표기 | 의미 |
|---|---|
| `미작성` | 해당 시나리오의 결과 문서가 아직 생성되지 않음 |
| `진행 중` | 테스트를 실행하거나 문제를 재현하는 중 |
| `분석 중` | 문제가 재현되어 원인과 개선 방법을 분석하는 중 |
| `BLOCKED` | 외부 결정, 다른 도메인 작업 또는 환경 문제로 진행할 수 없음 |
| `PASS` | 정의한 기대 결과와 정합성 조건을 모두 충족함 |
| `FAIL` | 기대 결과 또는 정합성 조건을 충족하지 못함 |
| `미실행` | 해당 환경에서는 아직 테스트하지 않음 |

`진행 중`, `분석 중`, `BLOCKED`는 현재 작업 상태를 나타낸다. 최종 테스트 결과는 `PASS` 또는 `FAIL`로 기록한다.

성능 테스트의 최초 Baseline은 임의의 목표 수치만으로 성공과 실패를 판단하지 않는다. 대신 실행 조건과 측정값을 남기고, 개선 후 동일한 조건으로 다시 실행하여 변화를 비교한다. 데이터 정합성 또는 보안 위반이 확인되면 Baseline 테스트에서도 `FAIL`로 판정한다.

## 테스트 유형별 도구

| 목적 | 사용 도구 | 주요 확인 대상 |
|---|---|---|
| API 흐름 검증 | Postman | 응답 코드, 응답 본문, 상태 전이와 권한 |
| 단위·회귀 검증 | JUnit | 도메인 규칙, 경계 조건과 수정 코드의 재발 방지 |
| 동시성·부하 검증 | k6 | 처리량, 응답시간, 오류율과 동시 요청 결과 |
| 데이터 정합성 확인 | PostgreSQL SQL | Reservation, Payment, Seat Hold, Seat, Inbox·Outbox 상태 |
| Queue·Token 확인 | RedisInsight·Redis CLI | Queue 순번, 상태, Token과 TTL |
| Kafka 확인 | Kafbat UI | 이벤트 발행, Consumer Group과 Consumer Lag |
| 서버 지표 확인 | Prometheus·Grafana | CPU, 메모리, JVM, HTTP, DB Connection과 Kafka 지표 |
| 공통 E2E 자동화 | Shell Script·GitHub Actions | 서비스 실행부터 최종 상태 검증까지의 반복 실행 |

모든 도구를 매번 사용할 필요는 없다. 담당자는 시나리오의 목적과 테스트 유형에 필요한 도구만 선택하고, 결과 문서에 선택한 도구와 확인 항목을 기록한다.

## 디렉터리 구조

```text
docs/test-results/
├─ README.md
├─ S01-happy-path/
│  ├─ local-result.md
│  └─ staging-result.md
├─ S02-concurrent-seat-hold/
│  ├─ local-result.md
│  └─ staging-result.md
└─ S{번호}-{시나리오명}/
   ├─ local-result.md
   └─ staging-result.md
```

- `local-result.md`: 담당자가 로컬 통합환경에서 수행한 테스트 결과
- `staging-result.md`: 팀에서 대표 시나리오로 선정하여 스테이징에서 수행한 결과
- 스테이징 검증 대상이 아닌 시나리오는 `staging-result.md`를 미리 만들 필요가 없다.
- 실행할 때마다 결과 파일을 새로 만들기보다 동일한 결과 문서에 최신 최종 결과와 의미 있는 문제 해결 과정을 반영한다.

## 공용 실행 자료 위치

테스트 실행에 필요한 자료는 결과 문서가 아니라 실행 목적에 맞는 `scripts` 하위 디렉터리에서 관리한다.

```text
scripts/
├─ integration-test/
│  ├─ run.sh
│  ├─ seed/
│  └─ verify-*.sql
├─ postman/
│  ├─ tikitaka.postman_collection.json
│  └─ tikitaka.local.example.postman_environment.json
└─ load-test/
   └─ S{번호}-{시나리오명}.js
```

현재 존재하지 않는 디렉터리는 실제 공용 스크립트를 추가할 때 생성한다.

Postman Environment에는 실제 Access Token, 비밀번호 또는 Service Key를 저장하지 않는다. 공유 파일에는 변수명과 예시 값만 두고, 민감한 값은 각자의 로컬 환경 또는 GitHub Secrets를 사용한다.

## 결과 문서 작성 기준

결과 문서에는 테스트 유형에 필요한 항목을 선택하여 작성한다. 모든 항목을 형식적으로 채울 필요는 없지만, 다른 팀원이 같은 테스트를 다시 실행하고 결과를 판단할 수 있을 정도의 정보는 포함해야 한다.

### 공통 정보

- 시나리오 ID와 이름
- 테스트 목적
- 실행 일시와 담당자
- 실행 환경
- Branch와 Commit SHA
- 관련 Issue와 PR
- 사용한 테스트 도구
- 테스트 데이터와 초기화 여부
- 사전 준비사항

### 실행 및 결과

- 실행 명령 또는 요청 순서
- 사용한 Postman Collection·k6·SQL 등 재현 자료
- 기대 결과와 실제 결과
- API 응답 및 서비스별 최종 상태
- 필요한 경우 DB·Redis·Kafka 확인 결과
- 필요한 경우 응답시간·처리량·오류율 및 서버 지표
- `PASS` 또는 `FAIL` 판정과 근거

### 문제를 발견하고 개선한 경우

- 최초로 관찰한 증상
- 재현 조건과 영향 범위
- 확인한 원인
- 수정한 내용
- 수정 전후의 동일한 실행 조건
- 수정 후 결과
- 남은 제한 사항 또는 후속 작업

## Local 결과 작성 원칙

- 담당자의 작업 브랜치에서 로컬 Docker Compose 통합환경을 사용한다.
- 테스트 대상 서비스와 인프라 버전, 실행 조건을 기록한다.
- 부하 테스트에서는 부하 발생기와 서비스가 같은 PC의 CPU·메모리를 공유한다는 점을 명시한다.
- 성능 수치를 추정하지 않고 실제 측정값만 기록한다.
- 실패를 수정했다면 최초 실패 원인과 최종 재검증 결과를 함께 남긴다.
- 결과 문서와 재현 자료는 수정 코드와 같은 PR에 포함한다.

## Staging 결과 작성 원칙

- 로컬 시나리오가 안정화되고 관련 PR이 `develop`에 반영된 후 실행한다.
- 배포한 `develop`의 Commit SHA를 기록한다.
- 로컬에서 사용한 대표 시나리오와 핵심 검증 조건을 유지한다.
- 로컬 전체 부하를 그대로 반복하지 않고 스테이징 자원 규모에 맞게 축소한다.
- 로컬과 결과가 다르면 애플리케이션, 컨테이너, 네트워크, 외부 연결과 서버 자원 중 원인을 구분한다.
- 테스트가 끝난 뒤 스테이징 자원 종료 여부와 남은 비용 발생 요소를 확인한다.

## 공통 판정 원칙

다음 항목 중 하나라도 발생하면 테스트를 `FAIL`로 판정한다.

- 서로 모순되는 도메인 상태가 저장됨
- 동일 명령 또는 이벤트가 중복 처리됨
- 다른 사용자의 리소스에 접근할 수 있음
- 위조되거나 만료된 인증·입장 정보가 허용됨
- 처리되지 않은 오류로 데이터가 유실됨
- 기대 결과와 다른 API 응답 또는 상태 전이가 발생함

성능 테스트는 최초 Baseline과 개선 결과를 동일한 조건으로 비교한다. 목표 수치는 팀이 근거와 함께 합의한 경우에만 성공 기준으로 사용한다.

## 문서 작성 시 주의사항

- 실제 JWT, Refresh Token, Service Key, 비밀번호와 개인정보를 기록하지 않는다.
- 요청·응답 예시는 민감정보를 마스킹한다.
- 측정하지 않은 값은 추정하지 않고 `미측정`으로 기록한다.
- 아직 결정되지 않은 정책은 성공 기준으로 임의 적용하지 않고 `확정 필요`로 표시한다.
- 로그 전체를 그대로 첨부하기보다 문제 판단에 필요한 구간만 정리한다.
- 실행 결과 이미지보다 재현 가능한 명령, 스크립트와 수치를 우선한다.
- 다른 서비스의 DB나 Redis를 직접 변경하는 방식을 정상 실행 절차로 사용하지 않는다.
- Seed와 상태 확인 SQL은 테스트 준비·검증 목적으로만 사용한다.
