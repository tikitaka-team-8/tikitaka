# 통합 테스트 실행 가이드

이 문서는 팀원이 같은 방식으로 통합 테스트 환경을 실행하고, 시나리오 자료와 결과를 일관되게 관리할 수 있도록 안내합니다.

테스트 결과와 진행 상태는 [통합 테스트 결과 안내](../test-results/README.md)에서 확인해 주세요.

## 진행 순서

```text
담당 시나리오 확인
→ 작업 브랜치 생성
→ 로컬 통합환경에서 최초 결과 확인
→ 문제 재현 및 원인 분석
→ 필요한 코드 보완
→ 동일 조건으로 재검증
→ 실행 자료와 local-result.md 작성
→ develop 대상 PR 생성
```

모든 로컬 시나리오가 안정화되면 최신 `develop`의 Commit SHA를 고정하여 스테이징을 배포합니다. 스테이징에서는 로컬 전체 테스트를 반복하지 않고, 팀에서 선정한 대표 시나리오를 통해 배포·네트워크·서버 자원에 따른 차이를 확인합니다.

## 공통 테스트 환경 실행

테스트용 공통 설정은 기본 로컬 실행용 `docker-compose.yml`과 분리하여 저장소 루트의 `docker-compose.test.yml`에서 관리합니다. 두 파일을 함께 지정하면 기본 실행 환경 위에 테스트용 설정이 추가됩니다.

```powershell
docker compose -f docker-compose.yml -f docker-compose.test.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.test.yml up -d --wait
docker compose -f docker-compose.yml -f docker-compose.test.yml ps
```

테스트가 끝나면 같은 파일 조합으로 컨테이너를 종료해 주세요.

```powershell
docker compose -f docker-compose.yml -f docker-compose.test.yml down
```

`docker compose down -v`는 PostgreSQL·Redis 등의 로컬 데이터를 함께 삭제합니다. 테스트 데이터를 완전히 초기화해야 할 때만 사용해 주세요.

`docker-compose.test.yml`에는 여러 시나리오가 함께 사용하는 테스트 설정만 작성합니다. 특정 시나리오의 실행 순서, 데이터와 검증 쿼리는 해당 시나리오 디렉터리에서 관리해 주세요.

## 실행 자료 구조

모든 테스트 실행 자료는 해당 시나리오 디렉터리 안에서 함께 관리합니다. 파일이 적을 때는 불필요한 하위 디렉터리를 만들지 않고 파일을 바로 배치해 주세요.

```text
scripts/test-scenarios/s09-queue-load/
├─ README.md
├─ queue-load.js
├─ run-vu.py
├─ verify-s09.py
└─ seed.sql
```

파일이 많아져 목적별 파일을 찾기 어렵다면 필요한 하위 디렉터리를 추가해 주세요.

```text
scripts/test-scenarios/s08-kafka-recovery/
├─ README.md
├─ run.sh
├─ seed/
├─ inject/
└─ verify/
```

| 위치 | 역할 |
|---|---|
| `scripts/test-scenarios/` | 시나리오별 실행 자료를 모아 관리합니다. |
| `s{번호}-{시나리오명}/` | 한 시나리오의 실행·준비·검증 자료를 함께 관리합니다. |
| `README.md` | 시나리오의 목적, 준비사항과 실행 순서를 안내합니다. |
| `seed/` | 테스트 시작 전에 필요한 데이터를 관리합니다. |
| `inject/` | 장애·실패·경합을 발생시키는 파일을 관리합니다. |
| `verify/` | DB·Redis·Kafka의 최종 상태를 확인하는 파일을 관리합니다. |
| `load/` | k6 등 부하를 발생시키는 파일을 관리합니다. |
| `postman/` | 해당 시나리오에서 사용하는 Postman Collection과 예시 Environment를 관리합니다. |
| `docs/test-results/` | 테스트 조건·결과·판정 근거를 기록합니다. |

모든 시나리오가 같은 하위 디렉터리를 가질 필요는 없습니다. 테스트에 실제로 필요한 파일과 디렉터리만 추가하고 빈 디렉터리는 미리 만들지 않습니다. 부하 테스트 파일도 해당 시나리오 디렉터리에서 함께 관리합니다.

## 테스트 유형별 도구

| 목적 | 사용 도구 | 주요 확인 대상 |
|---|---|---|
| API 흐름 검증 | Postman | 응답 코드, 응답 본문, 상태 전이와 권한 |
| 단위·회귀 검증 | JUnit | 도메인 규칙, 경계 조건과 수정 코드의 재발 방지 |
| 동시성·부하 검증 | k6 | 처리량, 응답시간, 오류율과 동시 요청 결과 |
| 데이터 정합성 확인 | PostgreSQL SQL | Reservation, Payment, Seat Hold, Seat, Inbox·Outbox 상태 |
| Queue·Token 확인 | RedisInsight·Redis CLI | Queue 순번, 상태, Token과 TTL |
| Kafka 확인 | Kafbat UI | 이벤트 발행, Consumer Group과 Consumer Lag |
| 서버 지표 확인 | Prometheus·Grafana | CPU, 메모리, JVM, HTTP, DB Connection과 Kafka 지표 |
| 공통 E2E 자동화 | Shell Script·GitHub Actions | 서비스 실행부터 최종 상태 검증까지의 반복 실행 |

모든 도구를 매번 사용할 필요는 없습니다. 시나리오의 목적에 필요한 도구만 선택하고, 결과 문서에 사용한 도구와 확인 항목을 기록해 주세요.

## 새 시나리오 추가 순서

1. `scripts/test-scenarios/s{번호}-{시나리오명}/` 디렉터리를 생성해 주세요.
2. 실행에 필요한 스크립트, Seed 또는 검증 SQL만 추가해 주세요.
3. `docs/test-results/S{번호}-{시나리오명}/local-result.md`에 실행 조건과 결과를 기록해 주세요.
4. 결과 안내 문서의 시나리오 상태와 결과 문서 링크를 갱신해 주세요.
5. 다른 팀원이 같은 방법으로 재현할 수 있는지 확인해 주세요.

새 컨테이너나 테스트 전용 공통 설정이 필요한 경우에는 개인 시나리오 파일에 중복하여 추가하지 않습니다. 먼저 팀에 공유한 뒤 `docker-compose.test.yml` 반영 여부를 결정해 주세요.

## 결과 문서 작성 기준

모든 항목을 형식적으로 작성할 필요는 없습니다. 다만 다른 팀원이 같은 테스트를 다시 실행하고 결과를 판단할 수 있도록 필요한 정보를 충분히 기록해 주세요.

### 공통 정보

- 시나리오 ID와 이름
- 테스트 목적
- 실행 일시와 담당자
- 실행 환경
- Branch와 Commit SHA
- 관련 Issue와 PR
- 사용한 테스트 도구
- 테스트 데이터와 초기화 여부
- 사전 준비사항

### 실행 및 결과

- 실행 명령 또는 요청 순서
- 사용한 Postman Collection·k6·SQL 등 재현 자료
- 기대 결과와 실제 결과
- API 응답 및 서비스별 최종 상태
- 필요한 경우 DB·Redis·Kafka 확인 결과
- 필요한 경우 응답시간·처리량·오류율 및 서버 지표
- `PASS` 또는 `FAIL` 판정과 근거

### 문제를 발견하고 개선한 경우

- 최초로 관찰한 증상
- 재현 조건과 영향 범위
- 확인한 원인
- 수정한 내용
- 수정 전후의 동일한 실행 조건
- 수정 후 결과
- 남은 제한 사항 또는 후속 작업

실행할 때마다 결과 파일을 새로 만들지 않습니다. 동일한 결과 문서에 최신 최종 결과와 주요 문제 해결 과정을 반영해 주세요.

## 환경별 작성 원칙

### Local 결과

- 담당자의 작업 브랜치에서 로컬 Docker Compose 통합환경을 사용해 주세요.
- 테스트 대상 서비스와 인프라 버전, 실행 조건을 기록해 주세요.
- 부하 테스트에서는 부하 발생기와 서비스가 같은 PC의 CPU·메모리를 공유한다는 점을 명시해 주세요.
- 성능 수치를 추정하지 말고 실제 측정값만 기록해 주세요.
- 실패를 수정했다면 최초 실패 원인과 최종 재검증 결과를 함께 남겨 주세요.
- 결과 문서와 재현 자료는 수정 코드와 같은 PR에 포함해 주세요.

### Staging 결과

- 로컬 시나리오가 안정화되고 관련 PR이 `develop`에 반영된 후 실행해 주세요.
- 배포한 `develop`의 Commit SHA를 기록해 주세요.
- 로컬에서 사용한 대표 시나리오와 핵심 검증 조건을 유지해 주세요.
- 로컬 전체 부하를 그대로 반복하지 말고 스테이징 자원 규모에 맞게 축소해 주세요.
- 로컬과 결과가 다르면 애플리케이션, 컨테이너, 네트워크, 외부 연결과 서버 자원 중 원인을 구분해 주세요.
- 테스트가 끝난 뒤 스테이징 자원 종료 여부와 남은 비용 발생 요소를 확인해 주세요.

## 공통 판정 원칙

다음 항목 중 하나라도 발생하면 테스트를 `FAIL`로 판정합니다.

- 서로 모순되는 도메인 상태가 저장됨
- 동일 명령 또는 이벤트가 중복 처리됨
- 다른 사용자의 리소스에 접근할 수 있음
- 위조되거나 만료된 인증·입장 정보가 허용됨
- 처리되지 않은 오류로 데이터가 유실됨
- 기대 결과와 다른 API 응답 또는 상태 전이가 발생함

성능 테스트의 최초 Baseline은 임의의 목표 수치만으로 성공과 실패를 판단하지 않습니다. 실행 조건과 측정값을 기록하고, 개선 후 동일한 조건으로 다시 실행하여 변화를 비교해 주세요. 목표 수치는 팀이 근거와 함께 합의한 경우에만 성공 기준으로 사용합니다. 데이터 정합성 또는 보안 위반이 확인되면 Baseline 테스트에서도 `FAIL`로 판정합니다.

## 주의사항

- 실제 JWT, Refresh Token, Service Key, 비밀번호와 개인정보를 기록하지 마세요.
- Postman 공유 Environment에는 변수명과 예시 값만 작성해 주세요.
- 요청·응답 예시에 포함된 민감정보는 마스킹해 주세요.
- 측정하지 않은 값은 추정하지 말고 `미측정`으로 기록해 주세요.
- 확정되지 않은 정책은 성공 기준으로 임의 적용하지 말고 `확정 필요`로 표시해 주세요.
- 로그 전체를 첨부하기보다 문제 판단에 필요한 구간만 정리해 주세요.
- 실행 결과 이미지보다 재현 가능한 명령, 스크립트와 수치를 우선해 주세요.
- 다른 서비스의 DB나 Redis를 직접 변경하는 방식을 정상 실행 절차로 사용하지 마세요.
- Seed와 상태 확인 SQL은 테스트 준비·검증 목적으로만 사용해 주세요.
